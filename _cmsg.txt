fix(tunnel): stop the address from drifting, and gate ready on a real check

The user reported that MCP seems usable by only one session at a time --
the browser and the desktop app, each on its own conversation, and one of
them always ended up unable to reach the server. The agent's error was
urlopen error [Errno -2] Name or service not known.

I first ruled the server out, because that was the obvious suspect:

  * two clients concurrently doing initialize + tools/list + tools/call
    -> all 200
  * 20 concurrent tools/call -> 20/20, 16ms
  * while one 40s call was in flight, another session's 5 calls all
    succeeded -- a slow call does not block anyone
  * six sequential calls through the public tunnel -> all 200

So the server was never the limit. Three defects on the tunnel side were
producing exactly the reported symptom.

1) The public address changed on every restart.

   trycloudflare hands out a random domain, and the app killed its tunnel
   on exit, so a restart always produced a new one: 100 starts in the log
   produced 94 distinct addresses. Whatever address the user pasted into a
   conversation died the moment the app restarted -- that conversation's
   agent then fails with a DNS error, while the one holding the newer
   address keeps working. That is indistinguishable from only one session
   being able to use it.

   The tunnel is now spawned detached with its output redirected to a file
   (not a pipe -- a pipe breaks when the parent dies), and the app no
   longer kills it on exit. Its pid/url/port are recorded in tunnel.json,
   so the next start reuses the same address when the process is alive, the
   port still matches, and a health check passes.

2) Ready was announced before the address actually worked.

   This was the nasty one. Measured on this machine:

      4s   cloudflared prints the trycloudflare address
      0s   DNS=ENOTFOUND
     52s   DNS=OK / HTTP 200

   The panel used to show the address as ready at the 4s mark, the user
   pasted it, and the agent failed instantly. Nothing was disconnected --
   the domain simply did not resolve yet.

   The address is now confirmed by an actual request before the state
   becomes up. Until then it stays pending and the panel says the address
   is still becoming active, with the connect button disabled, so a
   not-yet-working address is never handed over.

3) There was no way to recover without restarting the app.

   Added an address-dead-get-a-new-one button that drops the current
   tunnel and requests a fresh one.

Also added the multi-open entry point to the panel. The --profile backend
was already there and tested, but the only way in was running _multi.cmd,
which the user had no reason to know about. There is now a button that picks
a free slot and launches an instance with its own MCP port, config and Arena
session. Two details that matter: the child is spawned detached so it
survives closing the original window, and ELECTRON_RUN_AS_NODE is removed
from its environment -- otherwise electron.exe runs as plain Node and the
instance exits immediately with Cannot read properties of undefined
(reading commandLine). Every existing .cmd launcher clears that variable
for the same reason.

Verified: two instances listening on their own ports with independent
tunnels; the spawn path confirmed to survive its parent exiting; the
readiness gate confirmed to stay pending until a real request succeeds.
