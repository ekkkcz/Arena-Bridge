## 0. 摘要（先看这段）

调研中出现了一个必须先行澄清的关键事实，它直接改变了对该产品的判断：

| 常见预设 | 调研结论 |
| --- | --- |
| ShunCode 把网页端大模型封装成 OpenAI 兼容 API，供 Claude Code / Cursor 调用 | **不成立。** ShunCode 没有把网页模型变成 API，也没有做任何反向代理 |
| ShunCode 是"中转/反代"服务 | **不成立。** 官方免责声明明确写"不提供 API 中转、转售或代理服务" |
| ShunCode 靠卖模型额度赚钱 | **不成立。** 它明确"不自带模型、不做中转"，账号和额度始终是用户自己的 |

**它真正做的事**：把**你本机的项目工作区**变成一个 MCP Server，通过公网隧道交给**网页端的 AI Agent** 去调用。方向是——

```
ShunCode 的方向：  网页 AI（Agent） ──调用──▶ 本机工作区（MCP Server）
用户预设的方向：   网页模型 ──封装──▶ API ──调用──▶ Agent
```

也就是说，它不是"网页模型的搬运工"，而是"**本机能力的出口**"。它不碰模型，只碰工具。

**那"网页模型转 API"这件事在本机存在吗？存在——但不在 ShunCode 里，而在你本机另外两处**：`C:\VSCode\proxy-adapter` + `C:\VSCode\ccswitch-deepseek`（把 ChatGPT 订阅的 Codex 链路转成本地 OpenAI 兼容端点），以及桌面的 Arena 探测工具（浏览器注入式网页数据采集）。报告第 1.6 / 1.7 节对它们做了逐行级分析，它们是自研评估的真正参考样本。

### 1.2 ShunCode 的三条模型接入链路

据仓库 README 第 7–11 行与文档站，ShunCode 是**基于 Code-OSS 深度定制的本地 IDE**（不是 VS Code 插件，也不是纯 CLI），模型循环跑在独立 `agent-host` 进程，不写进 VS Code 内核。它同时提供三条互不替代的接入路径：

| # | 路径 | 协议/机制 | 是否需要付费 |
| --- | --- | --- | --- |
| 一 | **自定义 API** | OpenAI Chat Completions / Responses（文档另称支持 Anthropic） | 否 |
| 二 | **Codex 账号授权** | `auth.openai.com` 官方 OAuth 2.0 Authorization Code + PKCE | 否（但需自备 ChatGPT 订阅） |
| 三 | **Bridge 桥接** | 本机工作区 → Streamable HTTP MCP Server → 公网隧道 | **是（唯一收费点）** |

#### 路径一：自定义 API（与"网页转 API"无关的常规做法）
文档 `/docs/chat/api-key` 与 README「方式一」说明：在 `Agent Customizations` 里填 OpenAI 兼容的 `baseUrl` + API Key，自动从 `GET /models` 加载模型列表，Key 走 Secret 配置。**这是标准 BYOK，与网页端无关。**

#### 路径二：Codex 官方授权链路（"订阅账号 → API"的**合规**版本）
README 第 165–176 行给出关键细节：

- 走 `auth.openai.com` 的 **OAuth 2.0 Authorization Code + PKCE**；
- 浏览器完成授权，**不要求用户手动复制 access token**；
- **凭据格式与官方 Codex CLI 兼容，默认共享 `~/.codex/auth.json`**；
- 与官方 Codex CLI 复用同一登录状态；
- 使用 OpenAI Responses 协议 + 推理等级 + 并行 Tool Call。

> **技术要点**：这条路是"复用订阅额度"的正规姿势——**用厂商自己开放的 OAuth 流程拿 token，再喂给自家客户端**。它不需要逆向网页接口、不需要抓 Cookie、不需要伪造浏览器指纹。你本机的 `C:\VSCode\proxy-adapter\codex_auth_backup.json` 里保存的正是这套凭据（结构见 1.6 节）。

#### 路径三：Bridge 桥接（本产品真正的核心与卖点）

**这是理解 ShunCode 的关键，也是用户预设出现偏差的地方。**

文档 `/docs/bridge/overview` 原文：

> Bridge 把当前工作区的 MCP 工具通过公网隧道交出去。只要设备**能打开浏览器、能联网**……指挥你这台装着 ShunCode 的机器。**读写发生在本机，对端只看到工具返回的片段。**

文档 `/docs/advanced/mcp` 用一张表把方向说得非常清楚：

| 对比 | Chat 模式 | Bridge 模式 |
| --- | --- | --- |
| 谁当 Agent | 本机 Chat 模式里的模型 | **对面网站上的 Agent**（ChatGPT、Arena 等） |
| MCP 往哪走 | 你去连别人的 MCP（外接工具） | **你把自己变成 MCP，让对面来指挥本机工作区** |

Bridge 对外暴露的 MCP 工具集（README 第 180–186 行 + 文档）：

| 工具 | 能力 |
| --- | --- |
| `list_directory` | 查看目录直接内容，限制深度 |
| `find_files` | 按 Glob 查找，支持范围/排除/排序 |
| `search_files` | 文本或正则搜索，返回文件、行号、列号、有限上下文 |
| `read_files` | 批量读取/行范围，返回版本哈希 |
| `apply_patch` | 多文件原子化预检补丁，含冲突检测 |
| `lsp` | 符号、定义、引用、实现、Hover |
| `get_diagnostics` | VS Code 当前诊断（含未保存状态） |
| `run_command` | 持久真实 PTY 中执行前台/后台命令 |
| `get_command_output` | 按字节偏移**增量**读取长任务输出 |
| `send_command_input` | 向交互式命令/REPL 继续输入 |
| `wait` | 为后台构建提供合理等待，不高频轮询 |
| `set_todos` / `report_progress` | 在本地 UI 显示进度 |

### 1.3 它到底如何"拿到网页端模型的能力"

**答案：它根本不需要"拿到模型能力"。它借用的是网页 Agent 的「终端 + 外网」能力，反过来驱动本机。**

这是整个产品最巧妙的一步。文档 `/docs/bridge/clients` 给出了两种接法与**三个必要条件**：

> 只要同时满足下面三点，也可以连：
> 1. 支持 Agent（能自己调工具、跑任务）
> 2. **能使用终端**
> 3. **能访问外网**（才能连上你的 MCP 地址）
>
> 做法：每次新开对话，把提示词整段贴进输入框发出去……只有第一句比较特殊。

而"复制提示词"得到的原文形如：

```
https://xxxx.trycloudflare.com/mcp/<秘密路径>
快速连接这个 MCP（URL），明确使用规则，熟悉可用工具，做好处理接下来一系列工作的准备。
```

**技术链路完整还原（这是本报告的核心结论之一）**：

```
① 本机  ShunCode 起一个 Streamable HTTP MCP Server（默认监听 127.0.0.1:48271）
② 本机  cloudflared / ngrok 起隧道，把该端口映射到公网随机域名 + 随机秘密路径
③ 用户  把 MCP URL（或整段提示词）粘进网页 AI 的对话框
④ 网页  网页 Agent 用它自己的「终端」工具执行联网命令去连这个 MCP 端点   ← 关键跳板
⑤ 网页  Agent 通过 MCP 协议调用本机的 read_files / apply_patch / run_command …
⑥ 本机  ShunCode 在本地真实执行，只把工具返回的片段回传
```

**为什么这一步能成立**：因为新一代网页 AI（Arena Agent、Qwen Work、Manus、Browser Use 等）本身已经具备"跑终端命令 + 访问外网"的能力。**只要它能跑一条联网命令，它就能连上任意 MCP 端点**——厂商是否提供"自定义 MCP Connector"设置项反而不重要。文档正是这么说的：

> 官方不支持创建自定义插件 / 连接器 / MCP 的，用提示词也能连。
> **这不是破解，也不是高并发调接口。就是网页上正常开对话，只有第一句比较特殊。**

**已测试入口**（文档 `/docs/bridge/clients`，共 9 个，原文强调"不是全部"）：
ChatGPT（chatgpt.com）、Arena（arena.ai/agent）、WorkBuddy（workbuddy.cn/app）、Trae（work.trae.cn）、Qwen（qwenwork.cn/app/chat）、Manus（manus.im/app）、Browser Use（cloud.browser-use.com/agents）、Z.ai（chat.z.ai）、Agnes AI（app.agnes-ai.com）。

**这里回答用户问题中的"哪一种"**：

| 用户列举的技术手段 | ShunCode 是否采用 |
| --- | --- |
| 逆向网页接口 | **否**（官方明确否认，且无源码可证） |
| 浏览器自动化 | **否**（Bridge 不驱动浏览器；但内置浏览器只是方便用户打开站点） |
| 抓包模拟登录态 | **否**（不接触用户网页 Cookie） |
| 官方非公开接口 | **否**（用的是公开的 MCP 协议 + 公开的 Connector/提示词） |
| **反向外联（MCP Server + 隧道）** | **是，这是它的全部秘密** |

> **推测（非文档明示）**：步骤 ④ 中，网页 Agent 具体执行的命令大概率是 `npx mcp-remote <url>` 或等价的一次性 MCP 客户端。文档只说"快速连接这个 MCP（URL）"，未给出具体命令，故标为推测。

### 1.4 对外暴露的形态与 Agent 接入方式

| 维度 | 实现 |
| --- | --- |
| 形态 | **Streamable HTTP MCP Server**（文档明确"传输协议是 Streamable HTTP"） |
| 地址 | 公网隧道域名 + **随机秘密路径**；怀疑泄露可「重置 MCP 地址」，旧链接立即失效 |
| 本地端口 | 默认 `48271`（`shuncode.bridge.cloudflareNamedLocalPort`，取值 1024–65535） |
| 隧道一 | **Cloudflare Quick Tunnel**（默认）：零配置，仅需装 `cloudflared`；**每次启动地址都变**；官方未列月请求额度，最多 200 并发，无 SLA |
| 隧道二 | **Cloudflare Named Tunnel**：固定主机名，需 CF 账号+域名+Tunnel Token+Published application，Service URL 必须是 `http://127.0.0.1:<端口>` |
| 隧道三 | **ngrok 开发域名**：固定开发域名；免费额度约每月 20,000 次请求 / 1 GB 出站 |
| 就绪判定 | 隧道起来后还要过**公网健康检查**才报"已就绪"；`shuncode.bridge.startupTimeoutMs` 默认 20000 ms |
| 常驻 | `shuncode.bridge.persistentMode` 勾选后随应用自动启动 Bridge |
| 提示词定制 | `shuncode.bridge.customInstructions`，追加在内置说明之后，下次远端连接生效 |

**Agent 接入方式**：
1. **站点支持自定义 MCP Connector** → 直接把地址填进该站设置，填一次通常长期有效；
2. **站点不支持** → 每次新开对话把整段提示词发出去（旧对话不会记住这条 MCP）。

> **推测**：Bridge 之所以能"零配置接入任何站点"，本质是它把自己降级成了一个**普通 HTTPS 服务**，从而绕开了各家 Connector 生态的适配工作。代价是"每次新对话要重发提示词"这一体验缺陷，文档也如实承认了。

### 1.5 登录态 / 会话保活 / 流式 / 多账号 / 限流

这一节必须区分"ShunCode 侧"与"网页侧"——**ShunCode 几乎不管网页侧的登录态**，这是它与 chat2api 类产品的根本分野。

| 环节 | ShunCode 的处理 | 依据 |
| --- | --- | --- |
| **网页端登录态 / Cookie** | **完全不处理。** 用户在**内置浏览器**里自己登录（Bridge 页提供一键打开），Cookie 由该浏览器自己管 | `/docs/bridge/clients`「站点在内置浏览器里打开」 |
| **MCP 端点鉴权** | **以"地址即密钥"**：随机秘密路径；泄露则重置。**没有 OAuth / Bearer**（无法确认是否另有 header 鉴权） | `/docs/bridge/start` |
| **软件自身登录态** | GitHub 或 Gitee OAuth（Gitee 授权需 5 分钟内完成）；登录后显示**安装 ID**（设备标识） | `/docs/bridge/account` |
| **会话保活** | 靠**公网健康检查** + `persistentMode`；Quick Tunnel 重启换址；代理需开 TUN 才能让 cloudflared 的 QUIC/UDP 7844 通 | `/docs/bridge/start` |
| **流式输出** | **MCP 层不涉及流式**。工具调用是请求–响应；流式由网页侧 Agent 自己处理。`get_command_output` 提供的是**按字节偏移的增量读取**，不是 token 流 | README 第 136 行 |
| **多账号** | **文档完全未提及** → **无法确认**。授权是"账号 + 设备"绑定，同账号**最多同时 2 台有效设备**，新设备授权自动顶掉最久未活动的 | README 第 205 行 |
| **限流** | **服务端未做限流机制**（无相关文档）。真实的限流来自上游网页平台，由用户自己承受；文档反而把"额度不够"作为卖点由 Bridge 解决 | `/docs/intro` |
| **封号风险** | **官方明确承认并免责**："在国内，代理和网络仍可能触发风控、限制甚至封号。这不是 ShunCode 造成的，我们也不承担责任。" | `/docs/bridge/overview` |

> **一句话**：ShunCode 把"登录态/风控/限流"这三块最难啃的骨头**全部留给了网页平台和用户**，自己只做"本机工具出口"。这既是它技术风险低的原因，也是它必须靠"隧道授权"而不是"模型额度"收费的原因。

### 1.6 本机样本 A：真正的"订阅账号 → API"（`C:\VSCode\proxy-adapter`）

**这是本机最有价值的参考样本**，因为它展示了一条与 ShunCode 路径二同源、但更"野"的做法。

**文件清单**（只读）：

| 文件 | 大小 | 作用 |
| --- | --- | --- |
| `adapter.py` | 6,224 B | MiMo 图片过滤代理，监听 `:15722`，Anthropic 协议，向上游转发并递归剥离 `image` / `image_url` / base64 块 |
| `control.py` | 11,597 B | Tkinter 控制面板：启停两个服务 + **Codex 模式开关** |
| `config.json` | 1,200 B | 端口与多 provider 配置（**内含真实 API Key，本报告不予摘录**） |
| `codex_config_backup.toml` | 2,288 B | `~/.codex/config.toml` 备份 |
| `codex_auth_backup.json` | 4,295 B | `~/.codex/auth.json` 备份 |

**`codex_auth_backup.json` 的结构**（值已脱敏）：

```json
{
  "auth_mode": "chatgpt",
  "OPENAI_API_KEY": { ... },
  "tokens": ["id_token", "access_token", "refresh_token", "account_id"],
  "last_refresh": "2026-06-17..."
}
```

> 这就是**官方 Codex OAuth 登录后落盘的凭据集**（含 refresh_token 与 account_id），与 ShunCode 路径二"默认共享 `~/.codex/auth.json`"完全对应。

**`control.py` 的"模式开关"是整套机制的钥匙**：

```python
CODEX_CONFIG = ~/.codex/config.toml
CODEX_AUTH   = ~/.codex/auth.json

def detect_codex_mode():
    # auth.json 里 OPENAI_API_KEY == "adapter" 即为代理模式，否则为官方模式

def _switch_to_adapter():
    # 1) 若当前是真实登录，先把 auth.json 备份成 codex_auth_backup.json
    # 2) 恢复/写入 config.toml 的 provider 块：
    #    [model_providers.codex-adapter]
    #    base_url = "http://127.0.0.1:15723/deepseek/v1"
    #    wire_api = "responses"
    # 3) auth.json 写成 {"OPENAI_API_KEY": "adapter"}
```

**它的作用**：不改 Codex 客户端一行代码，只靠**改配置文件**就把 Codex 的模型后端从 OpenAI 官方**热切换**到本地代理（`:15723`），从而用 DeepSeek / Kimi / MiMo 驱动 Codex。`_switch_to_official()` 逆向操作即可还原官方模式，**备份机制保证了登录态不丢**。

**配套的协议翻译层** `C:\VSCode\ccswitch-deepseek\index.js`（19,572 B，Node.js）：

| 能力 | 实现要点 |
| --- | --- |
| 协议翻译 | **Responses API ↔ Chat Completions 双向转换**（Codex 用 Responses，多数国产模型只有 Chat Completions） |
| 路由 | 正则 `^/(deepseek|kimi|mimo)?(/v1/responses|/responses)$`，按前缀选 provider |
| 消息翻译 | `translateMessages()`：`function_call` → `tool_calls`、`input_text/output_text` → `text`、`input_image` → `image_url`（含 base64 转 data URI） |
| 角色映射 | OpenAI `developer` → `system` |
| 工具裁剪 | DeepSeek 限 128 个工具，超出按域名关键词优先级裁剪 |
| **DSML 恢复** | 修复 DeepSeek 把工具调用**以纯文本泄露**的问题（与 1.7 节 deepseek-web2api 的 DSML 方案同源） |
| 监听 | `127.0.0.1:15723` |

> **结论**：这条链路**完全合规**（走官方 OAuth + 官方 API 协议），难点只在**协议翻译**，不含任何逆向、抓包、指纹伪装。**它是自研时真正值得抄的部分。**

#### 关键机制逐项

**① 会话隔离 —— 每个实例一个持久化分区**（`src/main/browser-profile.js`）

```js
function partitionForBrowser(instance, runtimeNonce = '') {
  const key = instanceKey(instance);            // sha256(instance.id) 取 32 hex
  if (instance?.browser?.mode === 'incognito') {
    const nonce = runtimeNonce || crypto.randomUUID();
    const suffix = sha256(`${key}:${nonce}`).slice(0, 20);
    return `arena-incognito-${suffix}`;         // 一次性分区
  }
  return `persist:arena-${key}`;                 // 持久分区：登录态落盘、多账号互不干扰
}
```

**② 指纹伪装**：`normalizeBrowserSettings()` 管理 UA / 语言 / 时区 / 视口 / `deviceScaleFactor`；视口从 3 个预设（1365×768、1440×900、1536×960）中按 `sha256(instanceId)[0] % 3` **确定性选取**（同一实例指纹稳定）；UA 含 `/Users/` 等路径泄漏特征时回退为默认。

**③ 凭据加密**（`safe-storage-crypto.js` + `storage-adapter.js`）：走 Electron `safeStorage`（Windows 下即 **DPAPI**），密文 base64 存入 `secure.json`（`mode 0o600`），**换了机器/用户无法解密**。

**④ 页面桥**：`preload.js` 用 `contextBridge.exposeInMainWorld('arenaMac', {...})` 暴露约 40 个 IPC 方法（`startAuth` / `newAccount` / `switchAccount` / `startDraw` / `sendPelicanTest` / `listHistory` …），主进程用 `ipcRenderer.invoke` 处理。

**⑤ 核心采集 —— 页面内网络旁路（`src/assets/arena-model-probe.inject.js`，148,041 B）**

这是**整个工具技术上最硬的部分**，其设计文档注释（第 1008–1016 行）写得很直白：

> `interceptor.js — 页面内网络采集层（passive, 零侵入）`
> **原理：模型身份最硬的证据是"页面自己发出去/收回来的网络流量"。**
> 所以我们在页面最早的时机接管 fetch / XHR / EventSource，**旁路读取（clone）**，不改变任何请求行为，避免破坏页面。
> 目标：**< 800ms 内给出首判**（第一个 SSE chunk 到达即可判定）。

实测确认它同时挂钩了**四条通道**（不是只 hook fetch）：

| 通道 | 位置 | 做法 |
| --- | --- | --- |
| `window.fetch` | 第 1430–1433 行 | 包装后 `res.clone()` 旁路读 body，保留 `__orig`/`__probeOwner` 防重复包装 |
| `XMLHttpRequest` | 第 1439–1481 行 | 重写 `prototype.open/send`，在 `load` 事件里按 `content-type` 过滤后读 `responseText` |
| `WebSocket` | 第 1495–1520 行 | `addEventListener('message')` 旁路 |
| `EventSource` | 第 1523–1544 行 | 同上（SSE 主通道） |

采集到的"证据"分五类：`request.body.model`（请求体模型字段，权重 1.0）、响应头、SSE chunk 解析（`SSETap`）、`protocol.framing` 协议指纹、`reasoning.config` 显式推理档位（注释强调**绝不从耗时/Token 数/名称后缀反推**）。

**⑥ UUID → 真名映射**：Arena 请求里模型常是 UUID。工具用 `fetch(p, { credentials: 'include' })` 拉 `/leaderboard/agent`、`/leaderboard/text`、`/leaderboard`，解析 Next.js RSC 载荷 `self.__next_f.push([1,"<双重转义 JSON>"])`——注释坦承"直接正则切对象很脆弱（**实测两次失败**）"，改为**反转义 + 括号配平 + 逐个 `JSON.parse`**，且只在含 `publicName`/`provider` 时才采纳。映射结果存 `localStorage`。

**⑦ 登录自动化**（`auth-flow.js`，14,696 B）：一个显式状态机（`inspect → mail → mailbox/verify → passwordFilled → passwordSubmitted`），**8 分钟总超时**；遇人机验证时 `pauseForVerification()` **暂停等人手动完成**，检测到 `blocker` 消失后**自动继续**。登录页与 Arena 页分别读取状态。

**⑧ 自动注册**（`mailbox-fallback.js`，10,156 B）：多临时邮箱 provider（含 `Mail.tm`，`https://api.mail.tm`），随机本地部分 + 随机强密码注册，再用正则从邮件正文里精确提取确认链接：

```js
/https:\/\/arena\.ai\/nextjs-api\/callback\/email[^\s"'<>]*/gi
```
（并校验 host 必须是 `arena.ai`、path 必须是 `/nextjs-api/callback/email`）

**⑨ 限流退避**（`rate-limit-scheduler.js`，5,377 B）：这是设计得相当专业的一块。

- 退避档位：`[5, 10, 20, 30, 60]` 分钟，指数递增封顶；
- **优先采信上游官方信号**：`429` 时的 `Retry-After`（支持秒数与 HTTP 日期两种格式）、`resetAt`（自动判断秒/毫秒时间戳）；官方信号存在时 `official: true`，**不做本地退避**；
- 官方信号缺失时，**解析页面文案倒计时**，中英文通吃：
  `/(\d+)\s*(秒|分钟|分|小时)\s*(?:后|以后).*(?:重试|再试|继续)/` 与 `/(?:retry|try again|wait).*?(\d+)\s*(seconds?|minutes?|hours?)/i`
- 都没有才本地退避（`official: false`）；
- 状态持久化到 `rate-limit-state.json`（`0o600`，写临时文件后 `rename` 原子替换）；
- **刻意排除人机验证**：`if (signal.reason === 'recaptcha') return null;` —— 验证码不参与退避计时。

**⑩ 多实例与外置看门狗**：桌面另有 `Arena模型助手-0.1.2-看门狗增强版-20260918.zip`（**WebView2 / .NET Framework 4.6.2 实现，非 Electron**），内含**同名但字节数不同的 `arena-model-probe.inject.js`（144,811 B）**——这证明**注入脚本与宿主浏览器解耦、可跨 Electron/WebView2 移植**。其文档补充了几个一手运营数据：

- 账号文件 `account.dpapi`（**DPAPI 加密，绑当前 Windows 用户，换机无法解密**）；
- 每实例浏览器目录保留 `Network`（Cookies）但**每次启动清纯缓存**，上限 50 MB/实例；
- 限流节奏原文："Arena 侧有**按小时的额度窗口**……正常节奏：**等待 50~60 分钟 → 解封 → 干活几分钟 → 再次触发等待**"；
- "想提高整体产出：**保持多个实例同时在线**（实测实例少时反而更容易撞限流）"；
- 看门狗三级自愈：继续（保留当前轮）→ 重新开始 → 刷新整页；
- **刻意不自动恢复的例外**：条款弹窗、需重新登录、人机验证、账号被占用。

#### ⑪ 最关键的一条：**它根本没有对外 API**

> 该工具是 **GUI 桌面程序**，产物是「候选图集」和**导出 JSON/CSV 历史记录**（`preload.js` 里的 `exportHistoryJson` / `exportHistoryCsv`）。
> **它不监听任何端口，不提供 OpenAI 兼容接口，也不提供 MCP。**
> 换句话说：**它做了"网页模型转 API"里最难的前 80%（会话隔离 + 注入 hook + 证据链 + 限流退避 + 登录自动化），但没有做最后 20%（输出层）。**

这一点对自研评估极其重要——见第 3 节。

### 1.8 同类产品对照：真正的"网页 → API"是怎么做的

为回答"这类工具把网页模型变成 Agent 可用接口"的通用原理，补充两个有代表性的开源实现（二手来源，作者自述）：

**A. `lanqian528/chat2api`** —— 把 ChatGPT 网页版转成 OpenAI 格式

| 环节 | 做法 |
| --- | --- |
| 凭证 | `AccessToken`（登录后访问 `/api/auth/session` 取得）或 `RefreshToken`；**也支持完全免登录的 GPT-3.5** |
| 接口 | **完整 OpenAI 格式**：`POST /v1/chat/completions`，`Authorization: Bearer <token>`；Team 账号走 `ChatGPT-Account-ID` 头 |
| 流式 | 支持 `"stream": true` |
| **风控对抗** | `POW_DIFFICULTY`（默认 `00003a`）**工作量证明**；`PROXY_URL` 全局代理（**"出 403 时启用"**）；`EXPORT_PROXY_URL` 出口代理**防止拉取图片/文件时泄漏源站 IP** |
| 多账号 / 限流 | 多账号轮询（同时支持 Access/Refresh Token）、失败自动轮询下一个 Token、定时刷新（**每 4 天凌晨 3 点全部强制刷新一次**） |
| 会话保活 | `RefreshToken` 定时换 `AccessToken`；`HISTORY_DISABLED` 控制是否留 `conversation_id` |
| 官网镜像 | `ENABLE_GATEWAY` 开一个**官网原生镜像**，支持 `/?token=xxx` 直接登录、SeedToken 会话隔离 |

**B. `snake-aabb-wtf/deepseek-web2api-free`** —— 把 DeepSeek 网页版转成 OpenAI **+ Anthropic** 双格式

| 环节 | 做法 |
| --- | --- |
| 凭证获取 | **手动从 DevTools 复制**：`Authorization: Bearer` 的值 → `DEEPSEEK_TOKEN`；`Cookie` 整串（含 `cf_clearance`）→ `DEEPSEEK_COOKIES` |
| **鉴权对抗** | 自动求解 **WASM 工作量证明（`DeepSeekHashV1`）** |
| 接口 | `/v1/chat/completions`、`/v1/models`（OpenAI）+ `/v1/messages`（Anthropic） |
| 思维链 | 专家模式下分离 thinking token，走 `reasoning_content` 字段 |
| **工具调用** | **基于 DSML（DeepSeek Markup Language）提示词注入实现 function calling**，配 `StreamSieve` 流式筛分引擎逐字符检测工具调用标签 |
| 多账号 | 账号池轮询、idle/busy/error 状态、健康检查、自动恢复 |
| 限流 | **客户端**滑动窗口限流，按 API key 与 IP 独立计数，回 `X-RateLimit-*` 头 |
| 会话 | 自动创建/管理会话，可选多轮复用 |

**C. `jalabulajunx/WebBridge`** —— 另一条思路：**用 Chrome 扩展 + CDP 录制流量，自动生成 MCP Server**（"Turn any website into MCP tools"）。它的 README 有一段很重要的**风险自述**：

> Using WebBridge to interact with websites may violate those websites' Terms of Service... Automated access to websites can result in your **IP address being blocked, your account being suspended, or legal action**.

**三类做法的定位对比**：

| 路线 | 代表 | 凭证来源 | 风控对抗 | 维护成本 |
| --- | --- | --- | --- | --- |
| 逆向私有接口 + 转发 | chat2api、deepseek-web2api | 手工抓 Cookie/Token | PoW / Arkose / 代理池 / CF 盾 | **极高**（网页改版即失效） |
| 浏览器注入式采集 | Arena 探测工具、WebBridge | 宿主浏览器自带登录态 | 指纹伪装 + 限流退避 | 中高 |
| 官方 OAuth 复用订阅 | ShunCode 路径二、本机 ccswitch | **官方 OAuth** | **无需对抗** | **低** |
| MCP 反向外联 | **ShunCode Bridge** | 不碰凭证 | **无需对抗** | 低（只要 MCP 协议不变） |

### 2.2 收费作用于链路的哪一环

**答案：只作用于「公网隧道的启动权限」这一个点，且是硬门禁。**

文档 `/docs/bridge/license` 开头即写明：

> 启动 Bridge 前，当前账号必须有有效授权，并且**当前设备已授权**。

`/docs/bridge/overview` 再次强调：

> **没有有效授权、当前设备未授权时，无法启动隧道。** 不要先去配 Cloudflare / ngrok。

把它放进 1.3 节的六步链路：

```
① 本机起本地 MCP Server        ← 免费，无需授权
② 起 cloudflared/ngrok 隧道     ← ★★★ 收费闸门就在这里 ★★★
③ 用户粘 MCP URL 到网页
④ 网页 Agent 用终端连 MCP
⑤ 网页 Agent 调用本机工具
⑥ 本机真实执行并回传
```

**为什么这个位置选得精准**：

1. **它是整条链路唯一的"必经单点"**——没有隧道，公网就够不着你的本机，Bridge 功能归零；
2. **它极难被绕过**——用户当然可以自己去配 Cloudflare Named Tunnel / ngrok，但**授权校验发生在 ShunCode 进程内部**，不是靠"不给你域名"来限制的；
3. **它的边际成本几乎为零**——Quick Tunnel 用的是 **Cloudflare 免费额度**（文档原文："无需 Cloudflare 账号、Token 或域名"），ngrok 免费额度也归用户自己的账号；
4. **校验对象是"设备"而非"次数/Token"**——所以能打出"**不限次数、不限 Token**、隧道随便开"的口号而不亏本。

> **推测（非官方表述）**：其真实成本结构大致是——授权服务器（一个轻量订单/许可 API）+ 答疑人力（QQ 群 244627843，作者与老用户答疑）+ 可能的隧道超额流量。软件研发成本是沉没成本。以 ¥99/年 计，**毛利极高**，这解释了为什么它敢把单价压到"一杯奶茶钱"。

> **买的是服务，不是额度**

## 3. 自研可行性评估

### 3.0 先明确"自研什么"

用户的目标是"**我们能不能自己做一个这种软件/插件**"。由于 ShunCode 的真实形态与预设不同，**自研目标应拆成两个互相独立的问题**：

- **问题 A**：能不能自研"**让我的 Agent 用上网页端模型，且模型侧零成本**"？（= chat2api 路线，用户原本想做的）
- **问题 B**：能不能自研"**让网页端 AI 能操作我本机**"？（= ShunCode Bridge 路线，ShunCode 真正在做的事）

**两者难度、风险、收益完全不同，不能混为一谈。** 下面对四条候选路线逐条评估。

---

### 3.1 候选路线一：MCP 反向外联（ShunCode Bridge 路线）★ 推荐

**实现思路**

```
本地 MCP Server（stdio 或 HTTP）
   └─ 暴露只读工具起步：read_file / list_dir / search / git_status
隧道：cloudflared quick tunnel（零成本、零账号）
   └─ 或 ngrok / Cloudflare Named（要固定域名时）
出口：随机秘密路径 + 一次性 Token
接入：把 URL 贴给网页 Agent；或写入支持 Custom Connector 的站点
```

**工作量量级**：**小～中，3～7 天可出可用原型**

| 模块 | 工作量 | 说明 |
| --- | --- | --- |
| MCP Server | **0.5～1 天** | 直接用官方 SDK（TypeScript/Python）；或干脆用现成的 `@modelcontextprotocol/server-filesystem` |
| 隧道 | **0.5 天** | `cloudflared tunnel --url http://127.0.0.1:PORT` 一行命令，**无需任何账号** |
| 秘密路径/Token | 0.5 天 | 反向代理层加随机前缀即可 |
| 接入网页 Agent | **0.5 天** | 发提示词，零适配 |
| 加写能力（apply_patch / run_command） | 2～4 天 | **风险陡增，见 3.3** |

**主要难点**

1. **安全性是唯一的真难点**：MCP 地址一旦泄露 = 别人能在你机器上改文件、跑终端。ShunCode 的对策是"随机秘密路径 + 可重置 + 不公开"，**属于"靠不泄露来保证安全"，而非强鉴权**。自研时**至少应加 Bearer Token 或 mTLS**。
2. **Quick Tunnel 地址每次重启都变**，体验差；固定域名要 CF/ngrok 账号。
3. **国内网络**：cloudflared 走 QUIC/UDP 7844，**普通 HTTP 代理无效，必须开 TUN/全局代理**（文档已明确提示）。
4. 网页侧 Agent 的"终端"能力是**外部依赖**，平台一旦收紧就没得玩。

**结论**：**技术上完全可行，且是四条路线里性价比最高的一条。** 本机已具备全部前置条件（Node/Python、cloudflared 可一键装）。

### 3.2 候选路线二：抓包逆向 + 接口转发（chat2api 路线）

**实现思路**

```
① 浏览器登录目标站点 → DevTools 抓取 Authorization / Cookie（含 cf_clearance）
② 本地服务复刻该站的对话接口（含 PoW/Arkose 求解、SSE 解析）
③ 翻译成 OpenAI /v1/chat/completions 输出
④ Agent（Claude Code / Cursor）把 baseUrl 指向本地
```

**工作量量级**：**中～大，2～4 周出原型，但维护是无底洞**

| 模块 | 工作量 | 说明 |
| --- | --- | --- |
| 抓包 + 接口复刻 | 2～5 天/站点 | 需读懂该站 SSE 分帧、会话创建、附件上传 |
| **风控对抗** | **不可估** | PoW（DeepSeek `DeepSeekHashV1` WASM）、Arkose、Cloudflare 盾、行为风控 |
| 协议翻译 | 3～5 天 | 参考本机 `ccswitch-deepseek/index.js` 已有完整实现可抄 |
| 多账号池 | 2～3 天 | 轮询、健康检查、失效剔除 |
| 客户端限流 | 1 天 | 参考 `rate-limit-scheduler.js` |
| 工具调用 | 2～4 天 | 多数网页端无原生 function calling，需**提示词注入 + 流式解析**（DSML 方案） |

**主要难点**

1. **PoW / 验证码是会演进的军备竞赛**——你今天解掉 `DeepSeekHashV1`，明天它换算法；
2. **工具调用能力天然缺失**：这是**最致命的一点**。Claude Code / Cursor 类 Agent **强依赖 function calling**；网页端接口一般不暴露，只能靠提示词注入模拟，**可靠性显著低于原生 API**（deepseek-web2api 专门做了 `StreamSieve` 引擎就是被这个问题逼出来的）；
3. **封号**：见 3.3；
4. **合规**：见 3.3。

**结论**：**技术可行但强烈不推荐。** 投入产出比最差——你花 2～4 周做出一个随时可能失效、且工具调用不可靠的东西，去省 ¥99/年。

### 3.3 候选路线三：浏览器扩展 + 本地代理（DOM 注入 / CDP 录制）

**实现思路**

```
Chrome 扩展（内容脚本注入页面上下文）
   ├─ 方案 3a：像 Arena 工具那样 hook fetch/XHR/EventSource 旁路读流（只读观测）
   ├─ 方案 3b：像 WebBridge 那样用 CDP 录制流量 → 生成 MCP 工具
   └─ 方案 3c：直接操作 DOM（填输入框、点发送、读回复节点）
   ↕ Native Messaging / localhost WebSocket
本地代理服务 → 转成 OpenAI 兼容 API 或 MCP
```

**工作量量级**：**中，1～2 周**；且有**现成参考样本可复用**（见 3.4）

**主要难点**

1. **DOM 方案极其脆弱**——站点改一次类名就全废（Arena 工具用的是 hook 网络层而非 DOM，正是为了避开这一点）；
2. **仍是 ToS 灰区**，与路线二同源风险；
3. **需要用户保持浏览器开着且已登录**——这反而**降低了封号风险**（因为用的是真实浏览器指纹、真人节奏），是它相对路线二的最大优势；
4. **Chrome 扩展上架**：若走商店分发，会被以"违反第三方 ToS"驳回；只能开发者模式加载。

**结论**：**可行，且是本机素材最充分的一条**；但若目标是"给 Agent 当 API 用"，**收益仍不如路线四**。

### 3.4 候选路线四：官方 API / 官方 OAuth 聚合（最稳但无价格优势）

**实现思路**

- **4a**：聚合各家官方 API（OpenAI/DeepSeek/Kimi/MiMo/OpenRouter），对外统一成 OpenAI 兼容端点——**本机 `ccswitch-deepseek` 已经是这个形态**；
- **4b**：复用官方订阅的 OAuth 通道（Codex/Gemini CLI 等），把订阅额度转成本地端点——**本机 `proxy-adapter` 的 Codex 模式开关就是这套**。

**工作量量级**：**极小，1～3 天**

| 模块 | 状态 |
| --- | --- |
| Responses ↔ Chat Completions 翻译 | **本机已有**（`ccswitch-deepseek/index.js`，含工具裁剪、DSML 恢复、角色映射、图片块转换） |
| 配置热切换（不动客户端代码） | **本机已有**（`proxy-adapter/control.py` 的 auth.json/config.toml 备份-切换机制） |
| 多 provider 路由 | **本机已有**（`/deepseek/`、`/kimi/`、`/mimo/` 前缀路由） |
| 图片块剥离（适配不支持视觉的模型） | **本机已有**（`adapter.py` 的 `strip_images()`） |

**结论**：**几乎是"已完成"状态**。唯一缺点——**它不省模型钱**（仍按官方 API 计费）。但它**零合规风险、零封号风险、零维护成本**，是所有方案里最该优先做扎实的底座。

### 3.6 风险与边界

#### ① 服务条款 / 合规风险

| 做法 | ToS 风险等级 | 说明 |
| --- | --- | --- |
| 官方 API + 官方 OAuth（路线四） | **无** | 完全在授权范围内 |
| MCP 反向外联（路线一） | **低** | ShunCode 的免责声明称"仅利用第三方平台公开提供的自定义 MCP Connector 能力"。风险主要来自**平台后续收紧策略**，而非当下违规 |
| 浏览器扩展操控自己的已登录会话（路线三） | **中** | WebBridge 在 README 里明确自曝："may violate those websites' Terms of Service... may result in your **IP address being blocked, your account being suspended, or legal action**" |
| 抓包逆向私有接口 + 转发（路线二） | **高** | 直接违反多数平台"不得逆向、不得自动化提取、不得未经授权商业化利用"的条款（参见 OpenAI 使用条款 <https://openai.com/zh-Hans-CN/policies/row-terms-of-use/>；法律界对平台用户义务的通行归纳亦包含"不可私自复制破解、逆向修改产品，不可使用插件外挂"） |

**关键分界线**：**自用 vs 分发/收费**。
- **自用**：风险主要落在"账号被封"，属民事违约范畴；
- **分发或收费**：性质变化——可能触及**不正当竞争**、**破坏计算机信息系统**（刑法 285/286 条）、**帮助侵权**等，**风险量级完全不同**。

> **明确建议：无论走哪条路线，都不要把"逆向网页端模型能力"做成对外收费的产品。** ShunCode 恰恰是**主动避开了这条红线**（不做中转、不卖账号、只卖隧道服务），才敢公开收费并写免责声明。这一点值得认真对待——**它的"保守"不是技术能力不足，而是刻意设计的合规边界。**

#### ② 账号被封风险

- **ShunCode 自己承认**："在国内，代理、节点、网络波动仍可能触发风控、限制甚至封号。这不是 ShunCode 造成的，**我们也不承担责任**。"
- **chat2api 的现实**：需要 `PROXY_URL`（"出 403 时启用"）和 `EXPORT_PROXY_URL`（"防止请求图片和文件时泄漏源站 IP"）——**说明"IP 泄漏导致封号"是常态**。
- **Arena 工具的现实**：需要多实例、限流退避、指纹随机化，且文档明示"限流重试已达 5/5 次上限，仍被限流"。**免费额度也不是真的无限。**
- **降低风险的手段**（按有效性排序）：① 用官方 OAuth/API（零风险）；② 用浏览器扩展复用真实浏览器会话（低）；③ 住宅 IP + 真人节奏（中）；④ 数据中心代理 + 高频请求（高，基本必封）。

#### ③ 稳定性问题（网页改版导致失效）

这是**所有逆向类方案的结构性缺陷**，无法根治：

| 依赖点 | 失效触发 | 影响 |
| --- | --- | --- |
| DOM 选择器 | 前端改版 | 立即全废 |
| 私有接口路径/字段 | 后端迭代 | 立即全废 |
| PoW/验证码算法 | 风控升级 | 立即全废，需重新逆向 |
| SSE 分帧格式 | 协议调整 | 需改解析器 |
| MCP 协议本身 | 极少变（**标准协议**） | **几乎不失效** |
| 官方 OAuth/API | 厂商政策（有公告期） | 可控 |

> **Arena 工具的作者对此有清醒认识**——注释里写着"直接正则切对象**很脆弱（实测两次失败）**"，并因此改用括号配平 + 逐段 `JSON.parse` 的稳健解析。但**再稳健的解析也挡不住对方改协议**。
>
> **反过来看，ShunCode 的 Bridge 之所以稳定性最好，正是因为它把依赖放在了"标准 MCP 协议 + 通用公网隧道"上，而不是放在"某个站点的私有接口"上。这是它技术上最聪明的一个决策。**

#### ④ 其他边界

| 风险 | 说明 |
| --- | --- |
| **本机安全** | Bridge 泄露 = 他人可改你文件、跑终端。ShunCode 用"随机路径 + 可重置"缓解，**但这不是强鉴权** |
| **代码/数据外泄** | ShunCode 称"远程侧只看到工具返回的片段，仓库仍在本机"，**但工具返回的片段本身就可能含敏感代码**；README 提醒"对敏感仓库启用 Bridge 前，请确认第三方平台、隧道和组织安全政策允许该数据流向" |
| **供应链** | QQ 群分发的第三方工具（如 `Arena筛选助手`、`Chat-Plus`）**未经安全审计**；Arena 工具文档自己就写着"未验证程序本身的安全性" |
| **法律主体** | 收费需考虑经营资质、发票、消费者权益（退款）等 |

## 4. 结论与建议

### 4.1 结论：**建议「部分自研」——但自研的是路线一与路线四，不是路线二/三**

拆开回答用户的三个选项：

| 选项 | 判断 |
| --- | --- |
| 建议直接购买 | **部分成立**：若只要"用上网页端模型干本机活"，**直接买 ShunCode（¥99/年）比自研划算得多** |
| 建议自研 | **部分成立**：若你要的是"**自己的 Agent 用上网页端模型**"（路线二/三），自研在技术上做得到，但**不建议**——投入 2～4 周做出一个随时失效、工具调用不可靠、且有封号与合规风险的东西，只为省 ¥99/年 |
| **建议部分自研** | **✅ 推荐**：**路线四打底座（1～3 天，本机已完成 80%）+ 路线一加出口（3～7 天）**，两者都零合规风险、稳定性最好 |

### 4.2 理由（三条）

**理由一：ShunCode 的定价低于自研的机会成本。**
¥99/年 ≈ 一杯奶茶/月。自研路线二即便顺利也要 2～4 周，且此后**永久承担维护**（网页一改版就得跟）。按任何合理的人力成本折算，**这笔账在纯经济上不成立**。

**理由二：ShunCode 绕开了最难且最危险的部分，而自研很容易一头扎进去。**
它**不碰**登录态、不碰 Cookie、不做逆向、不卖额度——把风险全留在用户侧，自己只做"标准 MCP + 通用隧道"。**这是刻意的边界设计，不是能力不足。** 自研若从路线二/三切入，等于主动接过它躲开的全部风险。

**理由三：你本机已有两个高质量样本，自研的正确姿势是"组合它们"，而不是"复刻 chat2api"。**

- `C:\VSCode\proxy-adapter` + `C:\VSCode\ccswitch-deepseek` → **协议翻译 + 官方 OAuth 凭证切换**（合规、稳定、已跑通）；
- Arena 探测工具 → **多实例隔离、注入式采集、限流退避**（工程实现成熟，纯函数模块可剥离）。

**真正值得自研的，是把这两者的能力接起来**：用官方 OAuth/API 做模型底座（不省钱但省心），用 MCP 反向外联做"网页 Agent 操作本机"的出口（体验红利）。**这条组合路线，ShunCode 只做了后半段，前半段你已经有现成的了。**

### 4.3 推荐路线与第一步可落地动作

#### 推荐路线（按顺序执行）

```
阶段 0  验证（1 天，几乎零成本）      ← 先做这个，不要跳过
阶段 1  底座（1～3 天，本机已就绪）
阶段 2  出口（3～7 天）
阶段 3  可选：加写能力（谨慎，需先解决鉴权）
```

**阶段 0 · 最小可行性验证（**强烈建议作为第一步**，1～2 小时）**

> **目标：不写任何代码，先证伪/证实"网页 Agent 能否通过终端连上本机 MCP"这个核心假设。**

1. 装 `cloudflared`：`winget install --id Cloudflare.cloudflared --exact`
2. 起一个**现成的只读 MCP Server**（不要自己写），例如官方 filesystem server，监听本地端口；
3. 开隧道：`cloudflared tunnel --url http://127.0.0.1:<端口>`，拿到公网 URL；
4. 打开 Arena Agent（或 Qwen Work），**把 URL 用 ShunCode 文档里那种提示词发过去**：
   ```
   <URL>
   快速连接这个 MCP（URL），明确使用规则，熟悉可用工具，做好处理接下来一系列工作的准备。
   ```
5. **观察它是否真的能列出并使用你的本地工具。**

> **这一步的价值**：用 1～2 小时、零开发、零风险，验证整条路线是否成立。
> **如果跑通** → 阶段 1、2 照做，或**直接买 ShunCode 省掉阶段 2**；
> **如果跑不通**（平台封了终端外联）→ **说明整条路线的前提不成立，立刻停止自研念头，直接买 ShunCode 试一天（¥1）确认**，避免更大投入。

**阶段 1 · 底座（复用本机现成资产）**

1. 把 `ccswitch-deepseek` 的多 provider 协议翻译整理成一个常驻服务（**代码已存在，主要是整理与文档化**）；
2. 把 `proxy-adapter/control.py` 的"备份—切换—还原"模式开关固化成脚本（**注意：它的 config.json 里含明文 API Key，建议改为从环境变量/凭据管理器读取**）；
3. 目标：任何 Agent 客户端都能一键把 baseUrl 指向本地端点。

**阶段 2 · 出口（路线一）**

1. 用官方 MCP SDK 起一个本地 MCP Server，**只读工具起步**：`read_file` / `list_dir` / `search` / `git_status`；
2. `cloudflared` quick tunnel 暴露；
3. **务必加一层强鉴权**（Bearer Token 或 mTLS）——不要照抄 ShunCode 的"地址即密钥"；
4. 在网页 Agent 里跑通；
5. **确认稳定后，再考虑是否要加 `apply_patch` / `run_command`**。

**阶段 3 · 加写能力（可选，谨慎）**

- 若加，**必须**：白名单目录 + 命令黑名单 + 完整审计日志 + 二次确认；
- 参考 ShunCode 的 `apply_patch` 设计（上下文精确匹配、版本哈希防脏写、整包预检、失败不部分写入）——这套设计值得学。

#### 明确**不建议**做的事

| 不建议 | 原因 |
| --- | --- |
| 复刻 chat2api 式逆向并**对外收费/分发** | ToS 高风险 + 可能触及刑事红线，且维护无底洞 |
| 修改 Arena 探测工具 | ① 你已明确要求不改；② 改造量接近重写；③ 会破坏一个正在正常工作的工具 |
| 把 MCP 地址发到任何公开场合 | 拿到的人可以改你文件、跑终端 |
| 在敏感仓库上开 Bridge | README 已提示：需先确认平台/隧道/组织安全政策允许该数据流向 |
| 把 `proxy-adapter/config.json` 里的明文 Key 继续沿用 | 建议迁移到环境变量或 Windows 凭据管理器 |

### 4.4 一句话总结

> **"网页模型转 API"在技术上完全做得到，你的机器上甚至已经躺着两个半成品；但这条路的投入产出比很差——省下的是 ¥99/年，付出的是持续维护、封号风险和合规敞口。**

### C.1 对上述判断的回应：对作者成立，对使用者是反向信号

「大众传播 = 目标达成」这个推断，站在**工具作者**角度是合理的（若其目标是被认可、验证概念、积累影响力，传播即终点）。

| 维度 | 大众传播带来的后果 |
| --- | --- |

**证据 2 — `chatgate.ai` 对 Agent Mode 的介绍（引 Arena 发布说明）**：

> ✅ **结论：Arena Agent 模式是「模型 + 工具 harness」，具备 bash/终端、文件系统、联网与沙盒容器能力。这直接满足了前几轮悬而未决的前置条件——「网页 Agent 有没有终端」——答案是「有」。**

### D.2 为什么委托方的路线判断是对的（原则性区分）

必须把两类做法严格区分，它们在合规性上**性质不同**：

| 维度 | 反代类（`WebAI2API` / `arena2api` / `chat2api`） | **MCP 外联类（ShunCode Bridge 路线）** |
| --- | --- | --- |
| 流量方向 | **替客户端**向 Arena 发请求，伪装成浏览器 | Arena **自己**发请求（它本来就是 Agent） |
| 是否绕鉴权 | **要**：需窃取 Cookie、代解 reCAPTCHA、伪造 UA/IP | **不要**：不接触任何凭据 |
| 是否绕过 UI 限制 | **要**：需扩展隐藏模型、恢复被下架模型 | **不要** |
| 请求发起方 | 你的程序（第三方） | **平台自己的 Agent**（第一方行为） |
| 是否替代网页端 | **是**（把网页端当后端用） | **否**（网页端仍在原地，只是多了一组工具） |
| ToS §12 命中 | **(i) scrape + (k) circumvent security features** | 通常不命中 |
| 对抗性强弱 | **对抗性**（猫鼠游戏） | **协同性**（用平台公开能力） |

**关键洞察**：委托方的方案**没有"绕过"任何东西**——它是在 Arena **正常提供的** Agent 能力之上，追加一个**符合 MCP 标准的**工具端点。Arena 的 Agent 本来就要调工具，这只是**多了一个工具源**。

> 这也解释了 ShunCode 官方为何敢公开写「网页版接入**仅利用第三方平台公开提供的自定义 MCP Connector 能力**」并收费——它站得住脚。

### E.2 实测暴露的两个关键工程细节

**① 首次 `winget` 安装 cloudflared 后需重启终端**（PATH 不即时刷新）；实际路径 `C:\Program Files (x86)\cloudflared\cloudflared.exe`。

**② 鉴权模式必须双支持（路径 + 请求头）——这是实测踩到的坑。**
若只支持 `Authorization: Bearer` 头，则当网页平台的自定义 Connector **不支持自定义请求头**时，Agent 只会收到 401 而连不上。

> **这解释了 ShunCode 为何用「随机秘密路径」**：不是设计偷懒，而是**路径密钥是唯一能兼容所有网页平台的通用做法**。
> 更稳妥的自研做法是**两者都支持**，并在平台可配置请求头时优先用头。

**③ 本机系统代理 `http://127.0.0.1:65532` 不影响 cloudflared**（QUIC/UDP 直连），实测无需关闭。
